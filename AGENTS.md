# Проект: uptime-monitor

Мониторинг HTTP/HTTPS-сервисов: периодические проверки, история инцидентов,
уведомления в Telegram. Спецификация и критерии готовности — в [docs/PLAN.md](docs/PLAN.md).
Текущий статус: реализована основа Go-приложения с health endpoint, конфигурацией,
логированием и остановкой; мониторинг и PostgreSQL ещё не реализованы.

## Работа с владельцем

- Общение — на русском. Код, комментарии, имена, коммиты и продуктовая документация — на английском.
- После существенного этапа кратко объясняй в разговоре, что изменилось, зачем,
  как работает и какие компромиссы приняты. Учебные пояснения не помещай в продуктовые файлы.
- Реализуй текущую задачу, не весь план автоматически. Не добавляй независимые улучшения.
- README должен отражать доступное поведение; планы не выдавай за реализованные функции.

## Стек и границы

- Go 1.27.0: версия закреплена в `go.mod`; стандартная библиотека в приоритете.
- HTTP: `net/http` и `http.ServeMux`; REST API.
- PostgreSQL: `pgx/v5`, `pgxpool`; без промежуточного хранилища приложения в памяти.
- Миграции: goose в отдельном `cmd/migrate`, SQL встроен через `embed.FS`.
- Логи: `log/slog`; тесты: `testing`, table-driven tests, `net/http/httptest`.
- Один процесс и один активный экземпляр приложения в MVP, ограниченный пул исполнителей.
- Redis, брокер сообщений, gRPC, микросервисы и распределённый планировщик не входят в MVP.
- Решения записывай в `docs/adr/` по обязательным основаниям из раздела ниже.
  Изменение продуктового контракта, модели доступа или ограничения на один экземпляр
  согласуй с владельцем.

- Неполная обязательная документация означает неполную задачу: исправь её до готовности PR
  либо оставь Draft с конкретным перечнем недостающего.

## Обязательные основания для ADR

Каждое решение, которое вводит или меняет хотя бы один из пунктов ниже, должно быть
отражено в ADR в том же PR; не фильтруй решения по субъективной «значимости»:

1. Добавление или замена зависимости, инструмента либо внешнего сервиса.
2. Ответственность и взаимодействие компонентов, хранение данных и их жизненный цикл.
3. Контракт API, совместимость, стратегия изменения схемы и миграций.
4. Авторизация, доступ к данным и ограничения сетевого доступа.
5. Конкурентность, транзакции, повторы, доставка, обработка отказов и восстановление.
6. Выбор компромисса, ограничивающего будущую реализацию или эксплуатацию.

- Если решение уже описано и сохраняется, сослаться на существующий ADR достаточно.
  Для применения существующей стратегии миграций к новой таблице не нужен дублирующий ADR;
  новую схему и её поведение всё равно фиксируй в миграции, спецификации и тестах.
- Новое решение оформляй отдельным нумерованным ADR: контекст, рассмотренные альтернативы,
  выбор и причины, последствия/ограничения, статус и связанные документы.
- Существующий ADR можно дополнять, пока он описывает ещё не реализованный подход.
  При изменении реализованного подхода создай новый ADR, а прежний пометь как superseded
  со ссылкой на замену. Сохраняй прежние причины выбора; не переписывай историю решения.
- Имена переменных, выделение функции и форматирование сами по себе не требуют ADR.
  Если за таким изменением скрывается решение из списка, основание всё равно применяется.
- Перед PR перечисли новые/изменённые решения и покрывающие их ADR либо объясни,
  почему ни одно основание не применимо. Неотвеченные вопросы явно оставляй pending.
- Реестр и покрытие текущего проекта: [docs/adr/README.md](docs/adr/README.md).

## Организация кода

- `cmd/uptime-monitor` — сборка зависимостей, запуск и остановка.
- `cmd/migrate` — отдельная команда миграций.
- `internal/monitor` — домен, сценарии, правила инцидентов и необходимые интерфейсы.
- `internal/httpapi`, `internal/postgres`, `internal/probe`, `internal/scheduler`,
  `internal/notification` — адаптеры и фоновые компоненты по мере появления кода.
- Создавай пакеты по необходимости, без пустого каркаса и пакетов `utils`, `common`, `helpers`.
- Домен не зависит от HTTP, SQL и Telegram. Интерфейсы определяй у потребителя.
- Ошибки возвращай и оборачивай с безопасным контекстом; не используй panic для штатных отказов.
- `context.Context` — первый параметр операций I/O; передавай отмену и дедлайны до адаптеров.

## Twelve-Factor App

Основа: [12factor.net](https://12factor.net/). Применение к этому проекту:

1. **Codebase:** один Git-репозиторий, окружения используют его версии.
2. **Dependencies:** явные зависимости в `go.mod`/`go.sum`, фиксированные версии инструментов.
3. **Config:** конфигурация через окружение; секреты вне Git. `.env` — только локальный способ передачи env.
4. **Backing services:** подключение к PostgreSQL и внешним интеграциям через конфигурацию.
5. **Build, release, run:** сборка артефакта отделена от конфигурации и запуска.
6. **Processes:** важное состояние хранится в PostgreSQL; память содержит только временную работу.
7. **Port binding:** приложение само слушает порт из конфигурации.
8. **Concurrency:** масштабирование процессами — будущая возможность; MVP допускает только один
   экземпляр. Goroutines и worker pool ограничивают внутреннюю параллельность и не заменяют этот фактор.
9. **Disposability:** быстрый запуск, `signal.NotifyContext`, ограниченная по времени корректная остановка.
10. **Dev/prod parity:** одинаковый тип БД и миграции локально и в CI; Compose для локального запуска.
11. **Logs:** структурированные события в stdout, без файлов логов внутри приложения.
12. **Admin processes:** миграции и разовые операции запускаются отдельными командами.

Не заявляй полное соответствие всем факторам: ограничение одного экземпляра — осознанная граница MVP.

## Надёжность и безопасность

- Один монитор не проверяется параллельно сам с собой. Очереди и число goroutines ограничены.
- После перезапуска возобновляй расписание без массового воспроизведения пропущенных интервалов.
- Изменение инцидента и создание задания уведомления фиксируй одной транзакцией.
- Повторная доставка имеет ограниченные интервалы ожидания и обработку постоянных ошибок;
  не обещай exactly-once при неопределённом результате отправки Telegram.
- При остановке прекрати выдачу новых заданий, ограничь ожидание активных операций,
  закрой соединения после завершения работников.
- Управляющие API и UI требуют аутентификации; отсутствие конфигурации доступа не открывает их публично.
- Проверяй исходящие назначения: HTTP/HTTPS, запрет userinfo, локальных, приватных и служебных
  адресов IPv4/IPv6. Проверяй фактический адрес соединения, а не только строку URL;
  учитывай DNS rebinding. Редиректы в MVP не следуют автоматически.
- Небезопасный транспорт для тестов допустим только через тестовую зависимость, не production-флаг.
- Ограничивай время и размер входящих запросов и исходящих ответов; закрывай тела ответов.
- В логах и сообщениях ошибок не должно быть токенов, строк подключения, тел ответов,
  заголовков авторизации и полных URL с потенциальными секретами. Используй ID и категории причин.
- Применённые миграции неизменяемы. Не удаляй volumes и данные для исправления ошибок запуска.

## Проверки

- Для нового поведения: падающий поведенческий тест → минимальная реализация → рефакторинг.
- Домен и сервис проверяй без сети/БД; HTTP — через `httptest`; PostgreSQL — интеграционно.
- Интеграционные тесты используют отдельную тестовую БД и изолированные схемы.
  Локально допускается skip без `TEST_DATABASE_URL`; в CI БД обязательна, skip не заменяет проверку.
- Для планировщика используй управляемые часы/синхронизацию, без долгих sleep и внешних сайтов.
- Проверяй гонки, лимиты параллельности, отмену, перезапуск, границы переходов инцидента,
  неуспешную доставку уведомлений и запреты сетевого доступа.
- После появления Go-модуля: `gofmt`, `go vet ./...`, `go test ./...`.
  Для конкурентного кода — `go test -race ./...` в поддерживаемом окружении, в том числе Linux CI.
- Команды: `gofmt -w cmd internal`, `go vet ./...`, `go test -timeout 60s ./...`,
  `go build ./...`; с C-компилятором — `go test -race -timeout 60s ./...`.
  Linux CI запускает форматирование, vet, race-тесты и сборку. PostgreSQL и его
  интеграционные проверки появятся вместе с реализацией хранилища.
- Для изменений только документации проверяй diff, ссылки, согласованность
  требований и отсутствие секретов; не создавай фиктивные тесты.

## GitHub Flow

- Перед работой проверь status, ветку, remote, актуальную основную ветку и локальные инструкции.
- Одна связная задача: рабочая ветка → проверки/self-review → Conventional Commit → push ветки → PR.
- Используй `feat/`, `fix/`, `chore/`, `refactor/`; Git Flow и ветка develop не нужны.
- Сохраняй чужие и staged изменения. Не применяй автоматический stash/reset/clean.
- Перед коммитом проверь staged diff и секреты; перед push — remote и побочные эффекты workflows.
- В основную ветку напрямую не отправляй. Не запускай deployment или release без явного запроса.
- PR содержит результат и реальные проверки. Неполная задача или упавшие обязательные проверки — Draft PR.
- Просмотри CI; отсутствие CI не называй успешным прогоном. Merge и auto-merge требуют отдельной команды.
- После подтверждённого merge удаляй ветку лишь после fetch и проверки отсутствия невлитых изменений,
  зависимых PR и использования другим worktree; при squash/rebase проверяй перенос изменений.
- Не удаляй worktree и не переписывай историю без отдельного запроса.
